# `request_context`
[idempotency: not_idempotent] <!-- stateless; creates a new context per request -->

**Version:** 1.0.0 · **Tier:** Free · **Domain:** Platform / Observability

> Per-request context that carries a correlation ID, request ID, and scoped metadata across async boundaries, middleware chains, and service calls — without passing arguments through every function signature.

## Search Surface

### In plain language
Every incoming HTTP request gets a unique `request_id`. This ID is propagated through every log line, every database query, every outbound service call, and every error — so that when something goes wrong, all the related records can be correlated in your logging system. This contract also provides the mechanism to store per-request state (the authenticated user, tenant ID, feature flags) in a way that any function in the call stack can read without being explicitly passed the value. In Node.js this is `AsyncLocalStorage`; in Python it is `contextvars`; in Go it is `context.Context`.

### Use this contract when
- You need every log line for a request to include the same request ID
- You need to trace a request across multiple services with a correlation ID
- You need to access the current user or tenant from deep inside business logic without passing it as a parameter
- You are building a middleware that must propagate context to downstream service calls

### Do not use this contract when
- You need distributed tracing spans and traces → use `telemetry` (OpenTelemetry)
- You need audit log entries per operation → use `audit_log`
- You need to share state across requests (e.g. caching) → use `caching`

### Not to be confused with
- `telemetry` — distributed tracing with spans and traces; request_context is the lightweight per-request ID layer that feeds into telemetry
- `sessions` — per-user session lifecycle; request_context is a per-request scoped store, not a persistent session

### Also known as
correlation ID, request ID, X-Request-ID, request tracing, async context, request-scoped storage

## Request ID vs Correlation ID

| Concept | Scope | Source | Header |
|---|---|---|---|
| **Request ID** | Single HTTP request on a single service | Generated by this service at ingress | `X-Request-ID` |
| **Correlation ID** | Entire user action across multiple services | Generated at the first service (or by the client); propagated | `X-Correlation-ID` |

**Rules:**
- Generate a new `request_id` on every incoming request.
- If an incoming request already has an `X-Correlation-ID` header, preserve it. If not, set it to the `request_id` of the first service in the chain.
- Include both IDs in every outbound service call as `X-Request-ID` (new) and `X-Correlation-ID` (preserved).
- Include both IDs in every log line, every event payload, and every error response.

## Contract

### Functions

#### `createContext(request) → RequestContext`
Creates a new context for the incoming request. Reads `X-Correlation-ID` from the request headers (or generates a new one). Generates a fresh `request_id`. Stores both in async-local storage.

---

#### `getContext() → RequestContext`
Returns the current request context from async-local storage. Must be called from within the request lifecycle (within an async handler chain). Throws if called outside of a request context.

---

#### `setContextValue(key, value) → void`
Sets an arbitrary key-value pair in the current request context. Used by middleware to store resolved values (e.g. `auth_middleware` stores the resolved identity here after validation).

---

#### `getContextValue(key) → any`
Reads a value from the current request context. Returns `undefined` if the key is not set.

---

#### `propagateHeaders(outbound_request) → Headers`
Returns a headers object with `X-Request-ID` and `X-Correlation-ID` set for outbound HTTP calls. Attach to every service call made during the request lifecycle.

### Types

```typescript
type RequestContext = {
  request_id: string         // UUID v4, unique per request
  correlation_id: string     // UUID v4, shared across the full user action
  start_time: number         // Unix timestamp in ms
  method: string
  path: string
  ip: string
  values: Map<string, any>   // Scoped key-value store for middleware use
}

type ContextKey =
  | 'auth.identity'           // Set by auth_middleware after token validation
  | 'auth.tenant_id'          // Set by auth_middleware if multi-tenant
  | 'feature_flags'           // Set by feature flag middleware
  | string                    // Any custom key

type PropagationHeaders = {
  'X-Request-ID': string
  'X-Correlation-ID': string
}
```

## Standard Context Keys

| Key | Set by | Value |
|---|---|---|
| `auth.identity` | `auth_middleware` | Resolved `Identity` object |
| `auth.tenant_id` | `auth_middleware` | Tenant ID string |
| `feature_flags` | Feature flag middleware | `Record<string, boolean>` |
| `request.start_time` | `request_context` (auto) | Unix timestamp in ms |

## Invariants

1. **`request_id` must be a UUID v4 generated by this service.** Never trust a client-provided `X-Request-ID` as the `request_id` — only use it as a hint for correlation.
2. **`correlation_id` must be preserved if already present in `X-Correlation-ID`.** Never overwrite a correlation ID that arrived from a caller.
3. **All outbound HTTP calls must carry the correlation ID.** A service that drops the correlation ID breaks the trace chain for all downstream services.
4. **`getContext()` must throw a clear error if called outside of a request lifecycle.** Silently returning `null` hides bugs where business logic is called outside of a request context.
5. **Context must not be shared across concurrent requests.** Each request must have its own isolated context store.
6. **Context must survive async boundaries.** `AsyncLocalStorage` in Node.js, `contextvars` in Python, and `context.Context` in Go all guarantee this.

## Observability

Context data must appear in every structured log line:

```json
{
  "level": "info",
  "message": "order created",
  "request_id": "a3f7c12e-...",
  "correlation_id": "b9e2d41a-...",
  "user_id": "u_abc123",
  "tenant_id": "t_xyz789",
  "duration_ms": 42
}
```

## Failure Modes

| Scenario | Behaviour | Recovery |
|---|---|---|
| `getContext()` called outside request lifecycle | Throw `CONTEXT_NOT_FOUND` | Fix call site; context must be created before calling |
| Async boundary loses context | Context reads return `undefined` | Use `AsyncLocalStorage.run()` for all async operations |
| Correlation ID not propagated to downstream service | Trace chain breaks at that service | Add propagation headers to all outbound calls |
| Client sends malicious `X-Request-ID` | Ignore for `request_id`; accept as hint only | Always generate own `request_id` |
